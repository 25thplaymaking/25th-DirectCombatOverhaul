# AI Commander — Objective-Based Threat-Ranked Command System

**Date:** 2026-06-09
**Status:** Approved design (user sign-off on the 3 scoping decisions), pending spec review → plan → build
**Builds on:** existing lean `DCO_Commander.c` (vector reserves to the hottest fight) and the `DCO_TaskZone`
placeable pattern, `DCO_CompositionRegistry`/`DCO_GroupComposition` (owned compositions), the reinforcement +
vehicle-aware move primitives, and the Defend component.

---

## 1. Goals & Non-Goals

### Goals
- A battlefield director where **every group has an objective**, objectives are **ranked by threat**, and
  **orders are issued** to tackle them (assist under-attack units, defend undermanned bases, hold/patrol, commit
  reserves to the main effort).
- Objectives are **created automatically** (owned compositions, active fights, threatened areas) AND can be
  **placed by the GM**; both feed the same order pipeline.
- Objectives are **draggable, editable placeable entities** (reuse the Task Zone pattern) so the GM can move,
  re-prioritise, retype, add, or remove them live.
- Real C2 doctrine: **main effort + economy of force** — concentrate to win the decisive fight without stripping
  every other objective bare.
- Server-authoritative, AI-only, toggleable (extends `m_bEnableCommander`), default behaviour unchanged when off.

### Non-Goals
- No new game mode; no custom map-screen UI (GM interaction is via the editable placeable + entity attributes).
- Not a replacement for per-group DCO behaviours — the commander *directs*; the existing systems *execute*.
- No persistence/JSON of placed objectives beyond what the editor already saves with the scenario.

## 2. Architecture

### 2.1 Objective model — `DCO_Objective` (placeable editable entity)
A placeable editable entity modelled on `DCO_TaskZone` (so it is draggable in GM for free and carries editor
attributes). Fields:
- `m_eType` (`DCO_EObjectiveType`: DEFEND / HOLD / ATTACK / PATROL / SUPPORT / RESERVE)
- `m_iPriority` (0–100 GM bias added on top of the computed threat score)
- `m_fRadius` (area of the objective)
- `m_Faction` (which faction owns/should service it) — defaults to the GM's editing faction / placement
- runtime: `m_aAssignedGroups`, `m_fThreatScore` (computed), `m_bAutoGenerated` (true for auto, false for GM-placed)

**GM-placed objectives are real editable entities** (authored, draggable, saved with the scenario).
**Auto-generated objectives are lightweight non-entity records** held by the registry (NOT spawned entities — avoids
runtime entity churn/replication cost); they are drawn for the GM but are not draggable (you can't drag an
auto-detected fight). Both kinds feed the same scoring + order pipeline.

### 2.2 Objective registry — `DCO_ObjectiveRegistry`
Plain singleton (order-independent). Holds all live objectives (GM-placed + auto). Responsibilities:
- **Auto-derivation** each commander tick:
  - DEFEND objective per owned composition/base (via `DCO_CompositionRegistry`) — weighted up when undermanned.
  - SUPPORT/ASSIST objective at each in-contact friendly group under heavy threat (the hottest fights).
  - (Optional) ATTACK objective at a known enemy concentration/composition.
- Dedupe auto objectives against nearby GM-placed ones (a GM objective in the same area supersedes/feeds the auto one).
- Expire stale auto objectives (fight ended, base secured).

### 2.3 Commander brain — `DCO_Commander` (extended)
Each tick (existing timer):
1. **Threat scoring** (METT-TC-lite) per objective:
   `score = enemyStrengthNearby * wEnemy + friendlyDeficit * wDeficit + underAttack * wContact + undermanned * wBase + m_iPriority (GM bias) − distancePenalty`.
2. **Rank** objectives; the top is the **main effort**.
3. **Assignment**: match free/uncommitted groups to objectives by need and proximity. Each objective gets enough
   combat power to handle its threat (main effort gets priority of force); remaining groups hold/economise.
4. **Order issue** via existing primitives:
   - DEFEND/HOLD → Defend component + position hold.
   - SUPPORT/ASSIST → reinforcement-eligible + vehicle-aware move to the objective.
   - ATTACK → move-to + engage.
   - PATROL → idle/patrol behaviour within radius.
   - RESERVE → hold at a rally, available for the next tick's main effort.
   Re-issue throttled per group (reuse the converge re-issue guard pattern) to avoid order spam.

### 2.4 GM integration
- **Drag/edit**: objectives are editable placeables — GM drags to reposition, edits type/priority/radius/faction
  in the entity attribute panel (new `DCO_Objective*EditorAttribute` classes, entity-scoped not global).
- **Visualisation**: an always-on Shape draw showing each objective (sphere coloured by type/threat) and,
  optionally, order lines from assigned groups to their objective, so the GM sees the current plan. Gated by a
  GM toggle so it can be hidden.

## 3. Threat-scoring model (METT-TC-lite)
- **Enemy**: nearby enemy strength (count/threat measure within the objective radius + a margin).
- **Troops**: friendly combat power assigned vs required → deficit drives "needs more force."
- **Mission/priority**: objective type base weight + GM `m_iPriority` bias.
- **Time/criticality**: under-attack and undermanned-base flags spike the score (must act now).
- **Terrain/distance**: distance penalty so the commander prefers servicing nearer needs with nearer reserves.
Weights are named constants (tunable), defaulting to: contact/under-attack dominant, then base-undermanned, then
enemy strength, then GM bias, then distance.

## 4. Order → primitive mapping (reuse, don't reinvent)
| Order | Executed via |
|---|---|
| DEFEND / HOLD | `DCO_DefendComponent` + position hold; undermanned base pulls reserves |
| SUPPORT / ASSIST | `DCO_SetReinforcementEligible(true)` + `DCO_VehicleUtil.OrderGroupMoveToPosition/Entity` |
| ATTACK | vehicle-aware move-to + engage (let combat AI + HVT take over on contact) |
| PATROL | idle/patrol within radius (existing idle behaviour) |
| RESERVE | hold at rally; eligible for next main-effort assignment |

## 5. Feasibility / build notes
- **Placeable GUIDs are Workbench-only** (like Task Zones): the `DCO_Objective` prefab + placeable registry
  entry + editor-attribute category need Workbench-assigned GUIDs. The script + `.conf` bodies are authored; the
  prefab/GUID creation is a Workbench step (duplicate the Task Zone placeable, as done before).
- **Auto-generated objectives** that are runtime-only entities: prefer NOT spawning real entities for them; the
  registry can hold lightweight non-entity objective records for auto objectives, and only GM-placed objectives
  are real editable entities. (Avoids runtime entity churn + replication cost.) Auto objectives are drawn via
  Shape debug; only GM-placed ones are draggable (you can't drag a fight that's auto-detected anyway).
- All engine touchpoints verified via the Reforger MCP before coding (per AGENTS.md).
- Heavy reuse of existing DCO systems keeps the new surface small.

## 6. Risks & open questions
- **Order/AI contention**: the commander's moves must cooperate with morale flee, standoff, HVT, etc. Mitigation:
  issue orders as the existing reinforcement/defend primitives already used by DCO (proven to coexist), throttled.
- **Threat-score tuning**: the weights need playtest tuning; ship sensible defaults as named constants.
- **GM viz cost**: order-line/sphere draws every tick — throttle + gate behind a toggle.
- **Compile environment**: the project currently can't fully compile (base-game `Tuple2`/etc. errors); this
  feature must be built clean but cannot be compile-verified until that environment issue is resolved.
- **"Fully automatic" + GM-placed integration**: dedupe rule (GM objective near an auto one supersedes it) needs
  to be explicit so they don't double-count.

## 7. Build approach
Large feature → build via writing-plans → subagent-driven execution with review agents (same proven flow as the
Base Settings tab). Phasing INTERNAL to the build (not separate releases, per "build it all at once"):
data/types → registry + auto-derivation → commander brain (scoring + assignment + orders) → placeable entity +
attributes → GM visualisation.
